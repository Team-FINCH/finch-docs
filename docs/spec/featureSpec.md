# 모의투자 앱 기능 명세서 (MVP 확정판)

- 문서 버전: v2.4
- 작성일: 2026-08-20 / 최종 수정: 2026-09-04
- 변경 이력:
  - v1.1 — 모의 결제를 예수금 충전 수단으로 재정의
  - v2.0 — 리뷰 반영: 예수금·리셋 정책 확정, 충전 취소 MVP 제외, 투자 회차 도입, Sprint 0 결정 항목 분리, AI 읽기 전용 데이터 계약 추가, MVP 범위 축소, 수익률 정의를 종목별 지표로 한정, 정책 값 통일(관심 종목 50개)
  - v2.1 — 검토 피드백 반영: 인증 명세 추가(2.1), 체결 직전 재검증 규칙 추가(7.3), 멱등성 키 규칙 추가(11장), 리셋 시 충전 한도 초기화 명시(1.1/2.3), 종목 순위를 확장 범위로 이동(12장), 데이터 원천을 한국투자증권 OpenAPI로 지정하고 S0-6·S0-7 신설(1.2)
  - v2.2 — **계좌 리셋·투자 회차 제거**(이슈 #27). v2.0 에서 도입한 회차 개념을 되돌린다. 계정 1개 : 계좌 1개(2.1), 2.3 절을 "계좌 초기화는 제공하지 않는다"로 대체, 누적 충전 한도의 기준을 회차 → 계정 전체로 변경(1.1/3.2), 원장 유형에서 회차 종료/시작 제거(8장), 매매 내역의 회차 선택기 제거(8장)
  - v2.3 — **초기 예수금 지급 제거.** 실제 증권 서비스가 가입만으로 돈을 주지 않으므로 계좌는 0원으로
    열리고 사용자는 충전부터 한다. 2.2 절을 "초기 예수금은 지급하지 않는다"로 대체, 1.1 확정 정책표·
    8장 원장 유형·12장 범위표 갱신. `초기 지급` 원장 유형은 남기되 발행하지 않는다(지급액이 설정값이라
    되살릴 수 있다). **프론트 구현 전제가 바뀐다** — 가입 직후 잔고 0, 매매 내역 빈 목록
  - v2.4 — **충전 절차를 4단계로 교체하고 출금을 신설한다.** 카카오페이 실제 API(테스트 CID)를 쓰기로
    하면서 결제창을 거치는 흐름이 생겼다(3.1~3.3). 결제 수단이 "가상 카드/가상 계좌이체" →
    "카카오페이/계좌이체"로 바뀐다. **3.4 출금 신설** — 예수금 전액 출금 가능, 별도 한도 없음,
    출금해도 누적 충전 한도는 돌아오지 않는다. 8장 원장 유형·필터에 `출금` 추가, 1.1 정책표·12장 범위표
    갱신. 7.3 의 "가격 변동" 문구를 "예수금 부족"으로 합쳤다(구분할 근거가 없다)
- 범위: MVP 기능 전체. AI 분석 로직 상세와 확장 기능 상세는 별도 문서.

## 0. 용어 정의

| 용어 | 정의 |
|---|---|
| 예수금 | 주문에 사용할 수 있는 가상 현금 잔액 |
| 모의 결제(충전) | 가상 결제 절차를 통해 예수금을 충전하는 행위 (실제 금전 이동 없음) |
| 계좌 | 예수금과 보유 종목을 담는 단위. 계정당 하나이며 초기화되지 않는다 |
| 원장 | 잔고 변동(충전·체결)의 원천 기록. 모든 파생 값(잔고, 손익)은 원장에서 계산 |
| 평가금액 | 보유 종목 수량 × 현재가의 합계 |
| 총자산 | 예수금 + 평가금액 |
| 평균 매수가 | 보유 수량 기준 가중평균 매입 단가 |
| 평가손익 | (현재가 − 평균 매수가) × 보유 수량 |
| 평가수익률 | 평가손익 ÷ (평균 매수가 × 보유 수량) × 100 |
| 체결 | 주문이 거래로 확정되는 것. MVP는 시장가 즉시 체결만 존재 |

| 수익률 표시 | 종목별 평가손익·평가수익률만 제공. 포트폴리오 전체 수익률·자산 추이는 확장 |

**시세 원천 호출 구조 원칙**: 팀이 앱키를 공유하면 호출 제한도 공유된다. 각 서비스가 외부 API를 개별 호출하지 않고, **시세 수신 워커가 중앙에서 한 번 호출해 내부로 배포**한다.

## 2. 계정, 인증, 예수금

### 2.1 인증

- 로그인 수단: **카카오 OAuth 2.0**. 자체 회원가입 폼은 제공하지 않는다.
- 최초 로그인 시 계정을 생성하고, 계정 생성 직후 계좌를 함께 생성한다.
- 서비스 인증은 **JWT**를 사용한다.
  - Access Token: 짧은 만료(예: 30분). 요청 헤더 `Authorization: Bearer <token>`.
  - Refresh Token: 긴 만료(예: 2주). 갱신 전용 엔드포인트로만 사용한다.
  - 만료 시 클라이언트가 Refresh Token으로 재발급하고, 재발급도 실패하면 로그인 화면으로 보낸다.
- 계정과 계좌의 관계: **계정 1개 : 계좌 1개.** 모든 주문·충전·조회는 그 계좌를 대상으로 한다.
- 탈퇴는 MVP 범위에서 제외한다.

> 선행 조건: 카카오 OAuth는 redirect URI 등록에 서비스 도메인이 필요하다. 도메인·HTTPS 발급이 인증 구현의 blocker다.

### 2.2 초기 예수금은 지급하지 않는다
- **가입 시 지급하는 예수금은 없다. 계좌는 예수금 0원으로 열린다.** (v2.3 변경)
- 실제 증권 서비스가 가입만으로 돈을 주지 않는다. 사용자는 **충전(3장)부터 하고** 매매를 시작한다.
  계좌 리셋을 없앤 것(2.3)과 같은 방향이다 — 실제 서비스에 없는 편의를 넣지 않는다.
- 지급이 없으므로 **원장에 `초기 지급` 행도 남지 않는다.** 갓 만든 계좌의 원장은 비어 있다.
  금액이 0인 행을 남기지 않는 것은 회차 전환 기록을 없앤 것과 같은 이유다 — 기록할 사건이 없다.
- 지급액은 서버 설정값(`finch.account.initial-cash`, 기본 0)이다. 시연에서 잔고가 있는 상태로
  시작해야 하면 이 값을 올리고, 그때는 `초기 지급` 원장 행이 다시 기록된다.

> **첫 화면의 결과** — 가입 직후 잔고는 0원이고 보유 종목도 없다. 매수하려면 충전이 먼저다.
> 프론트는 예수금 0을 오류가 아니라 **정상 초기 상태**로 다뤄야 한다.

### 2.3 계좌 초기화는 제공하지 않는다
- **계좌 리셋과 투자 회차는 v2.2 에서 제거했다** (이슈 #27). v2.0~v2.1 의 이 절이 정의하던 기능이다.
- 실제 투자 서비스에는 계좌를 초기화하고 다시 시작하는 기능이 없다. 손실을 되돌릴 수 없는 것이 실제
  투자의 성질이고, 되돌릴 수 있게 만들면 연습용 서비스로 읽힌다.
- 투자 회차는 독립된 기능이 아니라 리셋 시점을 경계로 원장을 나누던 부산물이라 함께 사라진다.
- 원장은 계정 생성부터 이어지는 하나의 연속된 시계열이고, 매매 내역은 그 전체를 조회한다.

## 3. 모의 결제 (예수금 충전 · 출금)

### 3.1 기능 개요
- 실제 결제와 유사한 절차(결제 수단 선택 → 금액 입력 → **결제창** → 확인)를 거치면 해당 금액만큼 예수금이 충전된다.
- **카카오페이는 실제 API를 쓴다** (테스트 CID). 실제 금전 이동은 없지만 결제창·승인 흐름은 진짜다.
  계좌이체는 자체 모의 화면이다.
- 예수금은 **출금**할 수도 있다 (3.4). 초기 지급이 없어졌으므로(2.2) 충전이 매매의 시작점이다.

### 3.2 상세 요구사항 — 충전
- 입력: 충전 금액(필수), 결제 수단(**카카오페이 / 계좌이체**).
- 금액 입력: 직접 입력 + 프리셋 버튼(+1만 / +10만 / +100만).
- 한도: 1회 최대 10,000,000원, 계정 전체 누적 100,000,000원.
- **절차는 4단계다** — 결제 준비 → 결제창(카카오 또는 모의 이체) → 승인 → 확정.
  준비와 확정이 나뉘는 이유는 **사용자의 브라우저가 결제창으로 떠났다가 돌아오기** 때문이다.
  그동안 서버가 요청을 붙잡고 있을 수 없다.
- **예수금이 늘어나는 시점은 마지막 확정 단계 하나뿐이다.** 승인만으로는 돈이 움직이지 않는다.
  결제창에서 승인된 뒤 확정 전에 사용자가 창을 닫으면 예수금은 늘지 않는다.
- 확정 시 원장에 `충전` 유형으로 기록.
- 확인 화면: 결제 수단, 충전 금액, 충전 후 예수금 표시 후 최종 확인.
- **충전 취소는 제공하지 않는다.** 확인 화면에 "충전은 취소할 수 없습니다" 문구를 고정 노출한다.
- **같은 결제를 두 번 확정해도 예수금은 한 번만 는다.** 새로고침·네트워크 재시도로 확정 요청이
  두 번 도착하는 것이 정상 경로다.

### 3.3 예외 처리 — 충전
- 0원 이하 금액 입력 불가.
- 한도 초과: "충전 한도를 초과했습니다. (잔여 한도: N원)"
  - 한도는 **결제창에 가기 전에 한 번, 확정할 때 다시 한 번** 본다. 앞 검사는 편의이고 뒤가 진실이다 —
    그 사이에 다른 충전이 끼어들면 결제창까지 갔다가 확정에서 막힐 수 있다.
- 결제창을 띄우지 못함(PG 장애): "결제를 시작할 수 없습니다. 잠시 후 다시 시도해 주세요"
- 승인은 됐는데 확정에서 막힘(금액 불일치·한도 초과): 그 결제 건은 **실패로 굳는다.** 같은 건을 다시
  확정할 수 없고 처음부터 다시 해야 한다.

### 3.4 출금

- **예수금을 뺄 수 있다.** 입력은 금액 하나다.
- **출금 가능액 = 예수금 전액.** 별도 한도가 없다 — 잔고가 곧 상한이다.
- **출금 수단(은행·계좌번호)을 받지 않는다.** 모의 서비스라 받아도 쓰이는 곳이 없다.
- 출금 시 예수금 즉시 감소, 원장에 `출금` 유형으로 기록.
- **출금해도 충전 한도는 돌아오지 않는다.** 누적 충전액은 계좌 평생 기준이라 출금과 무관하다.
  되돌리면 충전↔출금을 반복해 누적 한도를 무한히 우회할 수 있다. 화면에도 이 규칙을 반영한다.
- 예외 처리 — 0원 이하 입력 불가. 잔고 초과: "출금 가능 금액을 초과했습니다. (출금 가능: N원)"

> **충전 취소(3.2)와 출금(3.4)은 다른 것이다.** 취소는 특정 충전 건을 되돌리는 것이라 그 돈이 이후
> 매매에 쓰였는지 추적해야 하고, 그래서 MVP에서 뺐다(1.1). 출금은 지금 잔고에서 빼는 별개 사건이라
> 건별 추적이 필요 없다.

## 4. 종목 검색

- 검색 대상: 국내 상장 종목(코스피/코스닥).
- 종목명 또는 종목코드 검색. 자동완성: 2글자 이상 입력 시 최대 10건, 종목명·현재가·등락률 표시.
- 결과 탭 시 종목 상세로 이동하며 최근 본 종목에 자동 등록.
- 최근 검색어 최대 10건 저장, 개별/전체 삭제.
- 예외: 결과 없음 빈 상태 화면. 거래정지 종목은 뱃지 노출 + 매수 불가.
- 초성 검색은 확장 범위.

---

## 5. 최근 본 종목

- 종목 상세 진입 시 자동 기록. 최대 30건, FIFO.
- 동일 종목 재조회 시 최상단 갱신(중복 없음).
- 표시: 종목명, 현재가, 등락률(상승 빨강/하락 파랑).
- 개별/전체 삭제. 서버 저장(계정 기준).

---

## 6. 관심 종목

- 종목 상세 또는 목록에서 토글로 등록/해제. **최대 50개.**
- 표시: 종목명, 현재가, 등락률, 등락 금액. 보유 중 종목은 "보유" 뱃지.
- 정렬: 등록순(기본), 이름순, 등락률순.
- 초과 시: "관심 종목은 최대 50개까지 등록할 수 있어요"
- 그룹·순서 편집은 확장 범위.

## 7. 종목 상세 (차트 + 매매)

### 7.1 기본 정보
- 종목명, 종목코드, 현재가, 전일 대비 등락 금액/등락률, 관심 종목 토글.
- 보유 중인 경우: 보유 수량, 평균 매수가, 평가손익·평가수익률 요약 카드.
- 시가총액·PER 등 부가 정보는 확장 범위.

### 7.2 차트 (MVP 최소 사양)
- 캔들 차트 1종. 기간 탭: 1개월 / 3개월 / 1년 (일봉 기준).
- 현재가는 시세 갱신 주기(S0-2)에 맞춰 갱신, 갱신 시각 표시.
- 분봉 차트·라인 전환·핀치 줌·크로스헤어·보조지표는 확장 범위. 분봉 도입 여부는 S0-4 결과에 따름.

### 7.3 매매 (시장가 전용)
- 주문 수량: 직접 입력 + 비율 버튼(10% / 25% / 50% / 최대).
- 주문 확인 화면: 종목명, 수량, 예상 체결 금액, 주문 후 예수금 표시 후 접수.
- 체결가 = 주문 시점 서버 최신 수신 가격. 접수 즉시 체결 처리.
- **체결 직전 재검증**: 확인 화면의 "예상 체결 금액"과 실제 체결가는 다를 수 있다(확인과 접수 사이의 가격 변동). 서버는 접수 시점에 최신 가격으로 필요 금액을 다시 계산해 예수금·보유 수량을 재검증한다.
  - 매수 시 예수금 부족: **주문을 거부**하고 "예수금이 부족합니다"를 안내한다. 수량을 임의로 줄여 체결하지 않는다.
    - v2.4 이전에는 이 경우를 "가격이 변동되어…"라는 별도 문구로 나눴으나, **가격 변동으로 부족해진 것과
      원래 부족했던 것을 서버가 구분할 수 없다** — 요청에 사용자가 본 기준가가 없다. 사용자가 할 일도
      양쪽이 같아서(다시 시도하거나 수량을 줄인다) 문구를 하나로 합쳤다 (apiSpec v0.8).
  - 매도 시 보유 수량 부족: 동일하게 거부하고 안내한다.
- 매수: 주문 가능 금액 = 예수금. 체결 시 보유 수량 증가, 평균 매수가 가중평균 재계산, 원장 기록.
- 매도: 주문 가능 수량 = 보유 수량. 체결 시 예수금 증가, 실현손익 계산, 원장 기록. 전량 매도 시 잔고에서 제거(원장은 유지).
- 예수금 부족 시 "충전하기" 이동 버튼 제공.

### 7.4 거래 시간·시세 예외
- 장외 시간: 주문 버튼 비활성화 + "지금은 주문할 수 없어요 (거래 시간 09:00~15:30)".
- 시세 수신 실패: S0-3에서 정한 허용 시간 내 마지막 가격 사용 여부에 따르며, 허용 범위를 벗어나면 주문 버튼 비활성화 + "시세를 불러올 수 없어 주문이 제한됩니다".
- 거래정지 종목: 매수/매도 비활성화 + 사유 안내.
- 보유 수량 초과 매도 불가.

## 8. 매매 내역

- 기록 대상(원장 유형): 충전, **출금**, 매수 체결, 매도 체결. (`초기 지급`은 유형으로 남아 있으나 지급 정책이
  없어져 현재는 기록되지 않는다 — 2.2)
- 표시(체결 건): 일시, 종목명, 구분, 체결가, 수량, 체결 금액. 매도 건은 실현손익·수익률 포함.
- 표시(충전 건): 일시, 결제 수단, 금액.
- 표시(출금 건): 일시, 금액. **결제 수단이 없다** — 출금은 수단을 받지 않는다 (3.4).
- 필터(MVP): 전체 / 매수 / 매도 / 충전 / **출금**. 정렬: 최신순.
  - **"충전" 필터는 모의 결제 건만 담는다. 출금은 들어가지 않는다.** 이 필터의 합계가 충전 한도
    화면의 누적 충전액과 같아야 하기 때문이다. 출금이 섞이면 두 숫자가 어긋난다.
  - 초기 지급이 없어졌으므로(2.2) 지금은 "전체"와 "충전"의 충전 건이 같다. 두 축을 합치지 않는 이유는
    **원장 유형과 화면 필터가 다른 축이기** 때문이고, 지급 정책이 되살아나면 그때 다시 갈린다.
- 계정 생성 이후 전체 내역을 한 목록으로 조회한다. 회차 선택기는 없다(2.3).
- 기간 필터·종목별 필터·매매 메모·월별 요약은 확장 범위.

## 9. 주식 잔고

### 9.1 요약 영역
- 예수금, 평가금액, 총자산(= 예수금 + 평가금액) 표시.
- 예수금 영역에 "충전하기" 바로가기.
- **포트폴리오 전체 수익률과 총자산 추이 그래프는 MVP에서 제공하지 않는다.** (충전과 얽힌 원금 정의가 확정된 뒤 확장 단계에서 도입)

### 9.2 보유 종목 목록
- 종목별: 종목명, 보유 수량, 평균 매수가, 현재가, 평가금액, 평가손익, 평가수익률(색상 구분).
- 정렬: 평가금액순(기본), 수익률순.
- 항목 탭 시 종목 상세로 이동.

### 9.3 데이터 처리
- 평가 값은 시세 갱신 주기에 맞춰 갱신, 갱신 시각 표시.
- 모든 표시 값은 원장에서 계산한 서버 값을 사용한다.

## 10. AI 연동 (MVP 범위와 데이터 계약)

### 10.1 역할 분리 원칙
- 백엔드(Spring): 원장과 시세의 단일 진실 공급원. 읽기 전용 API만 제공.
- AI 서버(FastAPI): 백엔드 API를 읽어 분석·계산·설명을 수행. 원장을 쓰지 않는다(잔고 변경 불가).

### 10.2 AI MVP 기능

MVP 범위는 사용자 대면 기능 6종이다. 응답 계약은 AI 서비스 API 명세(`docs/api/aiApiSpec.md`) §1, 프론트가 부르는 중계 경로는 API 명세(`docs/api/apiSpec.md`) §10을 따른다.

| 기능 | 화면 | 프론트가 부르는 경로 |
|---|---|---|
| AI 종목 분석 | 종목 상세 | `POST /api/v1/ai/stocks/{stockCode}/analysis` |
| Ask My Portfolio | 채팅 | `POST /api/v1/ai/chat` |
| 포트폴리오 진단 | 포트폴리오 | `POST /api/v1/ai/portfolio/diagnosis` |
| 수익률 원인 분석 | 홈 · 포트폴리오 | `POST /api/v1/ai/portfolio/attribution` |
| 주문 전 점검 | 주문 | `POST /api/v1/ai/orders/preview` |
| 데일리 브리핑 | 홈 | `GET /api/v1/ai/briefing` |

- 호출 경로는 프론트 → 백엔드 → AI 서버다. 프론트는 AI 서버를 직접 호출하지 않고, 백엔드가 위 경로를 AI 서버로 중계한다.
- 용어 설명은 별도 기능이 아니라 Ask My Portfolio 안에서 처리한다.
- 투자 논지 점검은 별도 기능이 아니라 AI 종목 분석의 한 섹션이다.
- 위 6종을 보조하는 기능으로 응답 피드백(`POST /api/v1/ai/feedback`)과 사용자 컨텍스트(위키) 조회·수정이 있다. 화면 슬롯이 필요하며, 위키 경로는 화면 범위가 확정되면 중계 경로에 추가한다.
- 매매 습관 분석은 확장 범위이며 별도 명세로 작성한다.
- 리밸런싱 제안, 목표주가·애널리스트 컨센서스처럼 특정 매매를 권유하는 형태의 출력은 규제 리스크로 MVP와 확장 모두에서 제외한다. 포트폴리오 진단과 주문 전 점검은 위험 지표를 제시할 뿐 매수·매도를 권유하지 않는다.

### 10.3 읽기 전용 데이터 계약 (초안, S0-5에서 필드 확정)

**GET /api/v1/portfolio** — 포트폴리오
```json
{
  "cashBalance": 1250000,
  "asOf": "2026-08-20T14:30:00+09:00",
  "holdings": [
    {
      "stockCode": "005930",
      "stockName": "삼성전자",
      "quantity": 10,
      "avgBuyPrice": 71200,
      "currentPrice": 73500
    }
  ]
}
```

**GET /api/v1/trades** — 거래 이력
```json
{
  "trades": [
    {
      "tradeId": 101,
      "stockCode": "005930",
      "side": "BUY",
      "price": 71200,
      "quantity": 10,
      "executedAt": "2026-08-18T10:12:44+09:00"
    }
  ]
}
```

- 필수 제공 필드: 보유 수량, 평균 매입가, 가용 예수금, 거래 시각·가격·수량, 종목 코드. 파생 지표(평가손익 등)는 AI가 계산해도 되고 백엔드가 함께 내려줘도 되며, 어느 쪽이 계산 주체인지 S0-5에서 확정한다.
- 인증: 서비스 간 내부 토큰. 사용자 식별자는 요청 컨텍스트로 전달.
- 페이징: trades는 커서 기반 페이징 지원(기본 100건).

## 11. 비기능 요구사항

- 모든 잔고 변동(초기 지급, 충전, 체결)은 서버에서 원자적으로 처리한다. 클라이언트 계산값을 신뢰하지 않는다.
- 동시 주문 등 경쟁 상황에서 예수금이 음수가 되지 않도록 서버 측 검증을 수행한다(원장 기준 잔액 검증 + 트랜잭션).
- **중복 요청 차단(멱등성)**: 충전과 주문 요청은 클라이언트가 요청마다 멱등성 키(UUID)를 생성해 헤더 `Idempotency-Key`로 전달한다. 서버는 이 키에 unique 제약을 두고, 이미 처리된 키로 들어온 요청은 **재처리하지 않고 최초 처리 결과를 그대로 반환**한다. 더블클릭과 네트워크 재시도로 인한 이중 충전·이중 체결을 막는 장치다.
- 금액 표기: 원화, 천 단위 콤마. 등락 색상: 상승 빨강, 하락 파랑.
- 시세 관련 세부 구현(캐싱 구조, 갱신 파이프라인)은 S0-1~S0-4 확정 후 설계서에 반영한다.
